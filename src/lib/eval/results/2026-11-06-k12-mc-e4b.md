# K-12 multiple-choice benchmark — `gemma4:e4b` — 2026-11-06

The first complete run of the pre-registered k12-mc set (240 items × 3 arms) on `gemma4:e4b`
(9.6 GB on disk, Q4_K_M, Ollama 0.40.15) on the same RTX 3070 laptop. It ran right after the e2b run
(`2026-11-06-k12-mc-e2b.md`), on the same code: master `372f06c`, dev app unmodified. The bar and rules
are in the header of `src/lib/eval/k12-fixture.ts` (#147). The run was not void: no ERROR rows, no
retried turns, no guard tripped. The shipping arm grounded 79/240 items.

## Verdict under the pre-registered bar

- **V (format validity): FAILED → FORMAT-INVALID, by one row.** No-parse must be ≤ 12/240 in *every*
  arm. Shipping had 5, but prompt-only had 13. The rule is per arm and was fixed before the run, so
  the result is FORMAT-INVALID and the accuracy figures above **are not quotable**, the shipping one
  included. The near miss is recorded here, not rounded away.
- **A (headline): would be MET.** The shipping Wilson lower bound is 93.6%, above 75%. Under V this
  is moot.
- **H (harness contribution): the harness reduces accuracy on this format.** Shipping vs raw, exact
  McNemar: b = 0, c = 8, p = 0.0078.
- **C (ceiling): met.** Raw is 240/240. The set cannot show a lift for this model.
- Shipping vs prompt-only (descriptive): b = 14, c = 5, p = 0.064. Grounded shipping rows were 78/79
  correct.

## Same mechanism as e2b, different failure

The kernel arms carry the tutor's output rules (step by step, one idea at a time, about 150 words,
at most one question). Like e2b, e4b sometimes sets up the first step and asks the student. The
difference is what it does next. **e2b guesses a letter. e4b mostly declines to give one.**

| | e2b prompt-only | e4b prompt-only | e2b shipping | e4b shipping |
|---|---|---|---|---|
| Replies ending in a question to the student before ANSWER | 67 | 19 | 51 | 6 |
| Wrong letters | 32 | 4 | 34 | 3 |
| No-parse: no ANSWER line at all | 0 | 9 | 7 | 2 |
| No-parse: a blank `ANSWER:` line | 14 | 4 | 11 | 2 |

`math-k5-14` (prompt-only) ends "What do you get when you multiply 3 by 1.35?" and stops. There is no
answer line, so the student is left with the question. `math-68-18` (shipping) writes `ANSWER: 328`,
the result of the first step (82 × 4), which it offers in place of a letter.

In the real app, where there is no forced answer line, that is the safer failure of the two. A
student gets a question rather than a confident wrong answer.

## What the two runs say together

- Both models know this material cold on their own (raw 237/240 and 240/240). On this format the
  tutor harness can only subtract, and it does: 50 items lost on e2b, 8 on e4b, none gained on either.
- The loss is in **whether the model commits**, not in what it knows. It is concentrated in math,
  where the output rules most often turn a calculation into "what do you get when…?".
- **Retrieval moves in opposite directions across the two models.** On e4b, shipping (with
  retrieval) beat prompt-only by 14 items to 5 (p = 0.064). On e2b, shipping lost 19 to 12 (p = 0.28).
  Neither is significant, and the pre-registration calls this contrast descriptive.
- Neither run is quotable as an accuracy figure. The quotable findings are the paired contrasts and
  the mechanism.

## Deviations, stated plainly

The same as the e2b run, which used the same code: #151 (the tokenizer, which can change which card
is retrieved), #155 (the `num_predict` cap, which never triggered: 0/720 rows stopped on length) and
#156 (UI only) all landed after the freeze. The `explain` skill layer rendered empty. A 2D game shared
the GPU, so the per-turn medians (4.3 s raw, 2.3 s prompt-only, 3.4 s shipping) are slower than on an
idle card. Grading is unaffected.

The 720 raw rows are kept outside the repo as `k12-e4b.json`, and every count above comes from that
file. Under rule 1 this first complete run is the result.
