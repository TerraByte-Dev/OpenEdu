# K-12 multiple-choice benchmark — `gemma4:e2b` — 2026-11-06

The first complete run of the pre-registered k12-mc set (240 items × 3 arms) on `gemma4:e2b`
(4.6 GB, Q4_K_M, Ollama 0.40.15), RTX 3070 laptop. The bar, rules and arms are in the header of
`src/lib/eval/k12-fixture.ts`, merged with the freeze (#147) before any scored item reached a model.
Run on master `372f06c`, the dev app running unmodified master (`git status` clean). The run was not
void: no ERROR rows, no retried turns, no guard tripped. The shipping arm grounded 79/240 items.

## Verdict under the pre-registered bar

- **V (format validity): FAILED → FORMAT-INVALID.** No-parse must be ≤ 12/240 in every arm; it was
  14 in prompt-only and 19 in shipping. By the pre-registered rule the shipping and prompt-only
  accuracies above **are not quotable as accuracy figures**. They are recorded here because the
  rules say the number is recorded either way.
- **A (headline): not met.** The shipping Wilson lower bound is 72.3%, below 75%. Under V this is
  moot.
- **H (harness contribution): the harness reduces accuracy on this format.** Shipping vs raw,
  exact McNemar: b = 0 items only shipping got right, c = 50 only raw got right, p ≈ 1.8 × 10⁻¹⁵.
  The pre-registration predicted "H will most likely be null". That prediction was wrong.
- **C (ceiling): met.** Raw is 98.8%, above 95%, so this set is near ceiling for this model and
  cannot show a harness *lift*. It can still show a harness *loss*, and it did.
- Shipping vs prompt-only (descriptive): b = 12, c = 19, p = 0.28. Retrieval made no measurable
  difference. Grounded shipping rows were 69/79 correct.

## Why: the tutor turns the question back to the student, then the format line forces a guess

The two kernel arms share the tutor system prompt; raw has none. The prompt carries the app's output
rules: *"Help them learn this subject step by step"*, *"Keep replies under about 150 words … Introduce
one new idea at a time"*, *"Ask at most one question at a time."* Under those, e2b does what a tutor is
told to do: it sets up the first step and asks the student to do it. The benchmark's final line then
demands `ANSWER: <letter>` from a reply that never computed the answer, and the model either leaves it
blank or guesses.

`math-k5-16` (length of a rectangle with area 84 and width 7; key D, 12 cm). Raw computes 84 / 7 = 12
and answers D. Shipping:

> I can rearrange the formula to solve for the length: Length = Area / Width
>
> What is the length of the rectangle?
>
> ANSWER: B

Counted over the run:

| | raw | prompt-only | shipping |
|---|---|---|---|
| Replies whose last line before ANSWER is a question to the student | 0 | 67 | 51 |
| — of those, not correct | 0 | 35 | 43 |
| No-parse rows that were a blank `ANSWER:` line | — | 14 / 14 | 11 / 19 |
| Wrong letters that were A or B (keys are balanced, 5 per letter per cell) | 2 / 3 | 26 / 32 | 29 / 34 |
| Mean reply length (characters) | 748 | 410 | 450 |

The A/B skew is the signature of a guess, not of a misconception.

## What this does and does not mean

- It does **not** show that e2b knows less inside the harness. Raw shows it knows 237/240 of these.
- It **does** show that the tutor prompt makes e2b stop before the answer on a direct
  multiple-choice question, mostly in math. In the real app there is no forced `ANSWER:` line, so
  the student would see the question, not a guess. Whether that is a defect depends on intent: a
  student who asks "which is right?" gets a prompt to work it out, which is the teaching behaviour
  the output rules ask for. But when a reply *must* commit, as the forced line makes it, the
  committed letter is a guess stated with the same confidence as a computed one. That second part
  is a defect.
- This format cannot measure what the harness is for (grounding, citation, progression). The RAG
  held-out eval (`2026-11-06-heldout-test.md`) is the measure for that.

## Deviations, stated plainly

- Code changed after the freeze commit (`55679a6`) in files the run touches, none of them in the
  prompt, parser, system prompt or items that rule 3 freezes:
  - #151 (`b2bb0d9`) tokenizes non-Latin and accented text as words. It changes which library card
    the shipping arm retrieves for some queries. The items are English, so the effect should be
    small, but it is not zero.
  - #155 (`55ea8bd`) bounds Ollama generation at the context window (`num_predict`). No row stopped
    on length (0/720), so the cap never triggered.
  - #156 (`f191ea3`) rewords the citation chip, which is UI only.
- The `explain` skill is resolved by the runner, but its bundle layer rendered empty in the system
  prompt dumped after the run. The prompt the kernel arms ran with is the six output rules plus the
  identity, approach, rules and subject blocks, about 1.1 KB.
- Hardware was shared: a 2D game (RotMG) was running on the same GPU. That affects only the per-turn
  times (median 1.8 s raw, 1.0 s prompt-only, 1.4 s shipping), not grading.

The 720 raw rows are kept outside the repo as `k12-e2b.json`. Every count above comes from that file.
Rerunning `window.__runK12Eval()` on this commit gives a fresh sample, not these exact rows, and under
rule 1 this first complete run is the result.
