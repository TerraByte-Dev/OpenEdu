# k12-flow (attempt-first) — lever L1 A/B — `gemma4:e2b`, `gemma4:e4b`, `qwen3.5:4b` — dev — 2026-11-07

> **DEV, not a test result.** These are the 240 k12-mc items, which are DEV for this flow
> (`docs/BENCHMARKS.md` section 0). Their rows were read for this file. Do not quote these numbers as
> a benchmark result. The detectors have not passed the hand-label check (κ ≥ 0.8), so nothing here is
> frozen.

Lever L1 (`docs/BENCHMARKS.md` section 3): on the turn whose user message is exactly
`SHOW_ANSWER_MESSAGE`, the kernel swaps the output rules for `WORKED_ANSWER_RULES`
(`src/lib/kernel/outputRules.ts`). PR #184, issue #183. Prompt-wording iteration **1 of 3**. The
wording was written before any run and not changed after.

The kill rule was posted in PR #184 before the first run: kill if, on any model, G1 drops by more than
2 points, or no-commit at T3 (G5 fail) is not at least halved.

## Verdict

**The kill rule does not fire on any model.** No-commit at T3 fell from 99 to 0 (e2b), 160 to 3 (e4b)
and 71 to 2 (qwen3.5:4b). G1 moved −1.2, +5.0 and −0.8 points. G3 rose by 40, 65 and 29 points, each
with exact McNemar p < 1e-18. The lever helps on two model families and hurts neither beyond its
threshold, so it counts as general on dev (rule 10).

## What the T3 replies did

| T3 | gemma4:e2b | gemma4:e4b | qwen3.5:4b |
|---|---|---|---|
| Has a line starting `Final answer` (base → L1) | 0 → 240 | 0 → 237 | 26 → 226 |
| Ends with a question | 175 → 0 | 221 → 0 | 3 → 0 |
| Commits a wrong answer (G5 and not G3) | 3 → 5 | 0 → 1 | 2 → 1 |

Every L1 miss, read by hand:
- **No commit, e4b (3):** math-k5-01, math-912-11, math-912-16. Each reply announces a `math.render`
  call ("I will render the calculation for the final steps:") and ends there. This is the baseline's
  "T3 stops before the final result" mechanism (15 e4b rows before, 3 now). The math-tutor skill's
  "you MUST call math.render" is the likely trigger.
- **No commit by the parser, qwen (2):** math-k5-09 ends "the decimal with the greatest value is
  **D) 0.62**"; science-912-15 ends "The correct choice from your list is **B) 2.0 A**". Both name the
  key. The G5 parser does not count either wording.
- **Wrong commit (e2b 5, e4b 1, qwen 1):** science-68-18 is wrong on both gemma models the same way
  (they call the described phase option B or C; key A). science-912-04 (e2b) works the key's value,
  20 kJ, then writes "The correct option is D", a letter-mapping slip (lever L4's target). ela-68-05,
  ela-912-01, social-68-20 (e2b) and ela-912-12 (qwen) argue for the wrong option.
- **Length cap, qwen (1):** ela-912-01 ran to 25,868 characters of visible planning ("The prompt asked
  to 'Show me the full worked answer,' implying…") and hit the cap. It still committed the key.

science-68-18 fails G3 in the e2b and e4b L1 arms and was the e4b false-praise example in the
baseline. It may be worth checking that item's key by hand.

## Detector validity

Not yet run. κ ≥ 0.8 against hand labels is still required before any of this is frozen. One known
limit points the same way in both arms: "This matches option C." and similar prose is not counted as
a commit. L1 asks for a `Final answer:` line, which the parser reads, so part of the G5 gain is
format. The baseline file estimates that counting prose commits would have lifted baseline G3 to
165 (e2b) and 142 (e4b); L1 is still +70 and +94 items above those figures.
