## Verdict

**The kill rule does not fire on any model.** No-commit at T3 fell from 99 to 0 (e2b), 160 to 3 (e4b)
and 71 to 2 (qwen3.5:4b). G1 moved −1.2, +5.0 and −0.8 points. On the old parser G3 rose by 40, 65 and
29 points, each with exact McNemar p < 1e-18. Rescored with #186, G3 rose by 30.4, 45.8 and 25.8 points
(p 4.0e-21, 6.3e-31 and 6.0e-17, so qwen3.5:4b no longer clears 1e-18), and no-commit at T3 fell from 75
to 0, 114 to 3 and 62 to 2. The lever helps on two model families and hurts neither beyond its
threshold, so it counts as general on dev (rule 10).

T1's request is byte-identical between arms (`turnRules.test.ts`, `parity.test.ts`), and Ollama
samples without a fixed seed. So the G1 changes are sampling noise. None is significant (McNemar
p = 0.76, 0.14, 0.82). The same holds for G1b, G2, G4 and the chip, which depend on T1 and T2 only.

So for this lever, which changes T3 only, the G1 clause measured noise and nothing else. Given the
discordant pairs here (41, 56, 20), a bare 2-point drop fires on noise alone with probability about
0.27, 0.25 and 0.13, so about one in two that it fires on at least one model. The verdict above stands
as pre-registered. `docs/BENCHMARKS.md` section 3 proposes a rule for future levers that change only
later turns. It is not applied retroactively. When a test shows the T1 request is byte-identical, G1
and G1b are descriptive, with no kill clause. (Revised 2026-11-08: the first version added a
significance condition, which could only ever fire falsely.)

## After the review: chip gate fix and confirmation run

### The gate (review finding 1)

At `775ee0e` the kernel swapped the rules whenever the newest user message was the chip's text. Typed
or pasted as a first message, it got a full reveal under rules that say the student tried. From
`1c404a9` the swap also needs the chip to have been offered under the reply before:
`offersShowAnswer` is the chip's one rule, called by `suggestFollowUps` (ChatTab's chips) and, through
`showAnswerOfferedAfter`, by the kernel on the saved conversation.

The k12-flow driver records `workedAnswerTurn` per row. This is not read from the kernel (corrected
2026-11-08). It is the same pure gate function, `isWorkedAnswerTurn`, evaluated by the driver on its own
copy of T3's history. So 240/240 agreement with `chipOffered` shows that the gate and the chip rule
agree. It does not show that `TutorEngine` swapped the rules. The swap did reach the model: in the
confirmation run, 208 of 209 chip-offered T3 replies have a `Final answer:` line, and 0 of 31 non-chip
replies do. The one exception, social-912-14, stops after a tool call. From commit `143a13a` the driver
also records `t3WorkedAnswerRules`, which comes from the kernel's own result: whether the system prompt
T3 sent ended with `WORKED_ANSWER_RULES`. The confirmation run predates it.

Offline proof before the confirmation run: over every row of the six runs above (baseline and L1,
three models, 1,440 rows), the new gate evaluated on the row's saved T1/T2 history equals the row's
recorded `chipOffered` on **1440 of 1440** (223, 204, 19, 217, 190 and 17 offered). No T1 or T2 reply
in those runs stopped early, so the stopped and length-cut paths of the gate are covered by unit tests
only, not by this data.

## Open questions

- **Rotate the scripted wrong letter in a future dev revision.** T2's wrong try is always the letter
  after the key, so a model's letter or position preference and anchoring on the student's letter give
  the same signal. A future revision of the k12-flow dev protocol could rotate the wrong letter across
  items by a fixed rule written before any run (for example key+1, key+2 and key+3, balanced within
  each subject and band). That changes T2's text on every item, so it would be a new protocol revision
  with its own baselines, not a change to these runs. The items are not changed now.
- **Should k12-flow's G3 be read over chip-offered items only?** Its T3 is sent whether or not the
  product would have shown the chip. In the confirmation run, most non-chip T3s give the answer and then
  ask a generic question, often in wording the parser does not read. Neither reading shows the product
  holding the answer back.
