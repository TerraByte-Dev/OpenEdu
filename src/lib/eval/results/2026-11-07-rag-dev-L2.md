What it buys on dev is **two items**, `h-xl-hi01` and `h-xl-ar01`, both a native-script spelling of a
note's name that fell below the retrieval floor. Both go from 0/3 to 3/3 on both models. At item
level that is 2 discordant items, both in L2's favour, on e2b: exact McNemar p = 0.5. On qwen a third
item, `h-xl-am03`, went the other way (majority pass 2/3 → 1/3), but its hits were identical in both
arms, so its reply request was too; that flip is sampling (qwen: 2 vs 1, p = 1.0). The retrieval part
is deterministic (the same hits every repeat), but n is 2 items. Do not read more into it than that.

## Reloads and the prefix cache

- **Reloads: none.** In all six completed runs the only call with `load_duration` ≥ 1 s is each
  run's first. The gloss call sends the same `num_ctx` as the turn, and Ollama kept the runner.
- **The cache-miss clause was weaker than intended.** The pre-registered rule compared
  `prompt_eval_count`. In Ollama 0.40.15 that count includes tokens served from the cache (every warm
  call reports ~1,400–2,500), so the rule could only catch a gloss call far longer than any English
  turn. It did not fire, but that is a weak check. Reported as written, not replaced.
- **What `prompt_eval_duration` shows (descriptive, chosen after the run):** e2b GPU: the first, cold
  call took 465 ms of prompt evaluation; gloss calls took 86 ms (p50) and the reply after a gloss
  52 ms, against 42 ms for warm English turns. e2b CPU: cold 4,070 ms for 1,566 tokens; gloss calls
  377–474 ms for ~1,450 tokens. A full re-prefill on CPU would cost ~4 s; none was seen. That holds for
  the gloss call. It does not hold for the reply after it: see "The prefix cache, per item" below. The
  reply after a gloss loses part of its cached prefix on CPU. qwen3.5:4b shows little prefix reuse in either arm (warm
  English 374 ms vs cold 750 ms), and its gloss calls (339 ms) are no worse than its normal turns.

## Known limits

- **n is small.** 12 cross-lingual dev items, 6 of them in a non-Latin script. The gain is 2 items.
- **e2b passed the cross-lingual clause at exactly 33/36.** One more miss would have killed it.
- **Latin-script languages are not glossed.** Spanish, French and Swahili already pass 6/6 here.
- **Harmful is a proxy.** No blind rubric pass on the 72 L2 cross-lingual rows.
- **One machine.** CPU timing is the GPU laptop with `num_gpu: 0`, not the reference box.
- **A gloss adds wrong notes (observed, not hypothetical).** Non-gold passages in context on the 18
  non-Latin rows: e2b 15 → 25, qwen3.5:4b 15 → 27, e2b CPU (12 rows) 10 → 17; grounding block median
  200 → 292 tokens. The harmful proxy only fires on a citation chip, so it reads 0 → 0 regardless.
- **The library half was never exercised on dev.** Every dev note is about a made-up thing, so no
  gloss could match a library card: 0 library candidates on all 144 GPU cross-lingual rows in both
  arms. "No gloss added a library card on dev" could not have come out otherwise.
  `gloss-edges.test.ts` covers the path headlessly with a real-topic Hindi question.
- **In-sample.** The lever was designed from these dev misses (6 of 10 were native-script names) and the
  whole gain is the two items that motivated it. This is not evidence against the ≥ 32/36 bar; that
  needs a test v1 or v2 run.
- **Long conversations are not measured.** The gloss call fits the history without the grounding
  block; if the block then pushes out one more history message, the reply's prefix diverges there.
  Every eval turn here is single-turn.

## Review follow-up, 2026-11-07

An adversarial review of PR #188 found eight issues. Code fixes are in `c707a89`; this section adds the
numbers the review asked for. The verdict table and pre-registration above are not re-scored.

### The prefix cache, per item (finding 1)

The pre-registered rule counts a cache miss on "a gloss call, **or the reply call of a glossed row**".
`prompt_eval_count` includes cached tokens in Ollama 0.40.15, so the count rule is close to blind; on
the CPU arms there is no warm English turn to compare against at all, so the rule cannot be evaluated
there (`analyze.cjs` now returns `null` for it instead of a count). The reply's prompt-eval time shows
what the count hides. CPU only (`num_gpu: 0`), e2b, each repeat:

| Item | Prompt tokens, base → L2 | Reply prompt-eval, base | Reply prompt-eval, L2 |
|---|---|---|---|
| `h-xl-hi01` | 1,403 → 1,561 (new block) | 179, 176 ms | 653, 654 ms |
| `h-xl-hi03` | 1,670 → 1,670 | 1,103, 1,033 ms | 1,033, 1,005 ms |
| `h-xl-ar01` | 1,396 → 1,678 (new block) | 150, 154 ms | 1,029, 1,041 ms |
| `h-xl-ar03` | 1,564 → 1,623 | 705, 674 ms | 753, 766 ms |
| `h-xl-am01` | 1,609 → 1,668 / 1,609 | 559, 546 ms | 979, 770 ms |
| `h-xl-am03` | 1,673 → 1,673 | 703, 692 ms | 1,000, 1,030 ms |

Reply after a gloss, all 12: p50 989.5 ms. Where the prompt is the same length in both arms, `am03`
pays about +318 ms (median 697.5 → 1,015) and `am01` repeat 2 +224 ms. The likely cause: in the
baseline the reply reuses the previous reply's `<context>` header from the cache; after a gloss call the
cache only matches up to the system prompt and tools, so about 115 tokens are processed again. On GPU
the same effect is about +9 ms per item.

**Restated clause:** pre-registered count rule: not fired on GPU, not evaluable on CPU; partial miss of
about 0.3 s per glossed reply on CPU. Whether a partial miss counts as "a cache miss appears" is for
Tate to decide; it is not decided here.

### Other review findings

- **Finding 2, English maths:** the first script check glossed "Find the eigenvalues λμ of A", "What
  does αβ mean in the decay?", "What is ℏω for a photon?", "Why is (αβ)γ = α(βγ)?" and "Solve 𝑥𝑦 = 3
  for y". `needsGloss` now votes by share (≥ 50% non-Latin among characters in words of 3+, Common and
  Inherited letters not counted). `english-path.test.ts` pins those five as new snapshot entries,
  written on `0188bf3` (master's kernel); the old gate fails them. On all 84 held-out items the
  classification is unchanged, so no dev row's retrieval path changed.
- **Finding 4, no deadline:** the gloss now has `GLOSS_TIMEOUT_MS` = 3 s, joined with the turn's abort,
  and a 128-token output cap; on timeout or error the turn retrieves on the original question alone. The
  largest measured gloss was 1.50 s (CPU) and 1.08 s (qwen3.5:4b GPU), so the deadline did not bind on
  any measured call. A CPU box slower than this laptop could lose the gloss, never the turn.
- **Finding 7, cloud providers:** L2 now runs only when `provider === "ollama"`. Cloud cost is
  unmeasured.
