# RAG grounding eval — qwen3.5:0.8b — 2026-11-06

P6 from `.dev/HANDOFF.md`: the first time the claimed 1.0 GB floor model has been run against the
RAG eval. Until today the only evidence for it was plumbing (preflight passes, tool calls parse).

## Configuration

| | |
|---|---|
| Model | `qwen3.5:0.8b` via Ollama, `think: false` (1.0 GB on disk) |
| Embedder | `nomic-embed-text`, 768-dim |
| Context | 8192 (`num_ctx`, the shipping default since #93) |
| Hardware | RTX 3070 laptop / Ryzen 7 5800H / Windows 11, with other apps holding ~3.5 GB VRAM |
| Fixture | 12 nonce-fact notes, 20 questions, 3 repeats × 2 mechanisms = 120 turns, 4.1 min |
| Commit | `feat/k12-benchmark-freeze` @ `ac8f068` (master `0236df4` plus eval-only commits; no kernel change) |

## Result

| Mechanism | positives | negatives | multi-hop | Spanish |
|---|---|---|---|---|
| **`always`** (grounding stage) | **36/36** | **9/12** | **6/6** | **5/6** |
| `off` (tool-only) | 6/36 | 12/12 | 0/6 | 0/6 |

**Bar: ≥80% positives AND zero fabricated citations. Result: 100% / three failures. NOT MET.**

The grounding stage does for a 1 GB model what it did for gemma4: 6/36 → 36/36 on positives and
0/6 → 6/6 on multi-hop. The harness, not the model, is what makes the small model answer from the
student's notes at all.

What fails is restraint on the questions the notes cannot answer.

## The three negative failures

| | retrieved (same every repeat) | failures | what the model did |
|---|---|---|---|
| n1 — boiling point of ethanol | Verrin lab log, Perrin's Star, Dalquist reagent | 2/3 | Correct answer (78 °C), then compared it to "the 214 °C cited in the student's lab notes" — the Verrin value leaks in |
| n4 — tallest mountain in the world | Ashcombe Ridge, World Physical Map, Perrin's Star | 1/3 | Answered from the Ashcombe Ridge note and showed it as a citation chip — a fabricated citation |
| n2, n3 | nothing above the floor | 0/6 | clean |

gemma4:e4b was handed the same adjacent passages on 2026-07-26 and declined to use them 12/12. The
0.8B model blends them in. Both failures happen only when retrieval puts a **topically adjacent but
non-answering** note in front of the model.

**Raising the note floor cannot fix this.** These are raw `nomic-embed-text` cosines for each question's
top note, recomputed outside the app the same way the app embeds them (unprefixed text, one chunk per note):

| question | top note | cosine |
|---|---|---|
| n1 — ethanol boiling point (negative) | Verrin lab log | **0.609** |
| s1 — Spanish, Verrin boiling point (positive) | Verrin lab log | 0.585 |
| s2 — Spanish, Brannock rye flour (positive) | Brannock recipe | 0.579 |
| n4 — tallest mountain (negative) | Ashcombe Ridge | 0.536 |
| lowest English positive (p11) | Course Admin | 0.734 |

The worst negative outscores both cross-lingual positives. Any floor that drops n1 also turns off
grounding for the Spanish questions. The top-1 vs top-2 gap separates them too, but only by 0.03,
which is overfitting at 4 negatives. Lexical coverage (the library ranker's IDF-mass fix) would
reject n1, because "ethanol" is in no note. It would reject the Spanish questions for the same
reason. The next step is a bigger fixture, not a tuned threshold: near-miss negatives (adjacent topic,
missing fact) and more non-English positives. Candidate gates should be judged on that fixture.

The one Spanish failure (s2) retrieved the right note and reasoned about it, but never stated 340 g.

## CPU-only throughput (measured outside the app)

Direct Ollama `/api/chat`, `think: false`, `num_ctx 4096`, temperature 0, a ~100-token tutoring
reply, mean of 3 after a warm-up. `num_gpu: 0` forces CPU only. These are not app turns: they omit
the system prompt and grounding block. At the measured prompt rate those add roughly 5–8 s.

| Config | generation tok/s | prompt tok/s | s per reply |
|---|---|---|---|
| 0.8b, CPU only, 4 threads | 21.3 | 409 | 4.9 |
| 0.8b, CPU only, 2 threads | 19.2 | 340 | 5.4 |

A Ryzen 7 5800H restricted to 2–4 threads is still faster per core than a refurbished office laptop.
Treat these numbers as a ceiling until the same probe runs on target hardware.

## Caveats

The same caveats as `2026-07-26-gemma4-e4b.md` apply:

- Retrieval is deterministic, so the repeats measure generation variance only.
- The fixture is deliberately favourable.
- The GPU run is not target hardware.
- With only 4 negatives, any retrieval fix tuned against them is overfit. Add held-out negatives
  before changing the floor.

## Reproduce

```js
// Settings → chat model qwen3.5:0.8b, then:
await window.__runRagEval({ repeats: 3 })
```
